# 流程瓶颈记录表：用了 AI，交付为什么还在等？

> **克劳德队长 · 评论「模板」领取**
>
> **对应文章：** 从“某大厂业务部门成为 AI Native 组织”的话题出发，检查个人提速有没有变成整条流程的交付提速。
>
> **用法：** 复制下面的表格，沿着“需求进入 → 制作 → 审核 → 交付”记录实际任务，对照使用 AI 前后的执行、等待和返工，判断瓶颈是否移动。

个人制作变快，不代表客户能更早收到交付物。省下来的时间，可能变成审核队列里的等待，也可能被需求变更和返工消耗掉。现有匿名案例缺少可核对的统计口径，不能据此确认其提效数字，也不能直接推到自己的团队。先把真实流程记下来，再判断下一步该改善哪个环节。

## 复制即用：记录口径

```text
【本次观察范围】

业务或交付物：
流程起点：需求实际进入的时间
流程终点：符合约定标准的交付物被接收的时间
完成标准：
时间口径：自然时间 / 工作时间（选定后前后保持一致）
观察方式：使用 AI 前后对照 / 同期相近任务对照

【统一定义】

执行时间：
本环节实际推进任务的时间。
如包含 AI 生成或工具运行，注明是否需要人员持续操作。
人员投入另行记录，不把机器运行时间直接当作人工工时。

等待时间：
任务没有推进、正在等待条件满足的时间。
写清在等什么，例如排队、补资料、确认、权限或外部反馈。

返工次数：
已提交的成果因未满足既定标准，被退回修改的次数。
新增需求单独记录，不混入返工。

返工时间：
返工发生的执行时间，已包含在执行时间中；
单列是为了分析原因，汇总时不重复相加。

交付总历时：
从需求进入到最终被接收的实际经过时间。
存在并行工作时，不能用各环节耗时简单相加代替。
```

## 复制即用：瓶颈判断清单

等待最长的环节值得检查，但单个任务里的一次长等待，还不足以证明它是流程瓶颈。

```text
【先检查记录】

[ ] 执行时间与等待时间分开记录。
[ ] 返工时间没有重复计入总耗时。
[ ] 新增需求与未达标返工分开记录。
[ ] 前后采用相同的时间口径和验收标准。
[ ] 并行工作没有被重复累加为交付总历时。
[ ] 缺失数据已经标明。

【再检查瓶颈】

[ ] 哪个环节反复积压待处理任务？
[ ] 哪个环节经常让后续工作无法开始？
[ ] 等待来自处理能力不足，还是资料、规则或确认缺失？
[ ] 制作提速后，审核是否出现更多排队？
[ ] AI 产出是否增加了核对或返工负担？
[ ] 原先的阻塞缓解后，是否出现新的持续阻塞位置？

【填写结论】

仍需排除的其他原因：
```

## 复制即用：让 AI 辅助复盘

```text
请根据我粘贴的流程记录，分析使用 AI 后，个人提速是否转化成了交付提速。

要求：
- 只使用记录中的数据，不补造耗时、比例或业务结果。
- 缺失字段标记为“证据不足”，不要当作没有发生。
- 分开分析执行、等待、返工、人员投入和交付总历时。
- 检查时间口径、重复计时、并行工作和对照条件。
- 区分记录直接支持的发现与尚需验证的推测。
- 不把单次长等待直接认定为持续瓶颈。
- 不把前后差异直接认定为 AI 导致。

请输出：
- 哪些动作有记录支持其变快，哪些尚无法判断。
- 节省的时间是否体现为交付总历时缩短。
- 当前最值得检查的阻塞环节及依据。
- 是否有证据支持瓶颈移动。
- 一个最小改善动作，以及下一轮需要补记什么。

流程记录：
（在此粘贴已填写的表格）
```
