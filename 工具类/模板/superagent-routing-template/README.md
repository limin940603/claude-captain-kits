# 消息分流规则模板（先规则、后模型）

克劳德队长 · 评论「模板」领取的那份

> 思路来自 DeepSeek Harness 团队公开的 Super-agent 架构文章（转载见公众号「赛博禅心」2026-10-31）。原文的两段委派提示词和「100 词」硬规定是原文内容；其他清单是我们按原文思路整理的模板，阈值都是建议值，按你自己的情况改。
> 适合：想让 AI 接进群聊、工单、邮件、GitHub，又怕它刷屏、乱接活、烧 token 的个人和小团队。

---

## 用法（4 步）

1. 先填「一、规则筛清单」：把你所有的消息入口列出来，每个入口定一档。这一步用普通代码或机器人平台自带的过滤就能做，不调模型。
2. 把「二、模型筛提示词」贴进负责判断的那个 AI（原文叫 Router）的系统提示词里，【】换成你的内容。
3. 把「三、群聊回复规范」也贴进去。
4. 如果有长时间跑的任务，按「五、巡查清单」配一个定时检查（每 15–30 分钟一次即可）。

---

## 一、规则筛清单（第一道，不调模型）

每个入口只能选一档：

| 档位 | 意思 | 典型入口 |
|---|---|---|
| 只响应明确请求 | 只有 @ 它、或带指定前缀（如「/ai」）才处理 | 大群、客户群 |
| 候选 | 进入第二道，让模型判断要不要管 | 产品反馈群、工单、PR 评论 |
| 忽略 | 直接丢，不进模型 | 闲聊群、通知群、机器人自己的消息 |

复制这张表填：

```
入口名称：【例：用户反馈群】
档位：【只响应明确请求 / 候选 / 忽略】
白名单（这些人或机器人的消息才看）：【可空】
黑名单（这些发送者一律忽略）：【至少填它自己，防止自己回自己】
直接丢弃的规则：
  - 纯表情、纯图片无文字
  - 少于【5】个字
  - 含【吃饭、外卖、下班、哈哈】等闲聊词，且不含【报错、白屏、bug、打不开、需求】等工作词
  - 机器人发的通知（CI 成功、打卡提醒等），除非是【CI 失败】
同一话题的后续消息：已经有人在办的，直接转给办这件事的那个 AI，不再进第二道
```

检查点：上线前拿最近一天的真实消息过一遍，看第一道筛掉了多少、有没有误杀工作消息。误杀了就把那个词加进「工作词」。

## 二、模型筛提示词（第二道）

```
你是【团队名】的消息分派员。你只负责判断和分派，不亲自干活。
每次你会收到一批新消息（可能一条，也可能几条一起），每条带编号、来源、发送人、内容摘要。
对每条消息给出一个决定，只能选一种：
- 忽略：闲聊、已经解决、与【你的业务范围】无关
- 派新活：一件具体的、可以动手的事（复现问题、改代码、查资料、起草回复），写一句任务描述
- 交给已有任务：属于【任务编号】正在办的事，写明编号
- 问人：缺关键信息、或需要负责人拍板，写一个最直接的问题
判断规则：
1. 拿不准要不要管时，选「忽略」，宁可少管不要刷屏。
2. 发现具体缺陷（能描述出现象），即使没人 @ 你，也可以派新活去后台复现；只有复现成功并找到简单修复时才对外说话。
3. 不自己写代码、不自己执行命令，所有动手的事都派出去。
输出格式（每条一行）：编号 | 决定 | 一句说明
```

## 三、群聊回复规范

原文硬规定（DeepSeek 称验证过，简单有效）：

```
单次回复不超过 100 词。
```

我们建议的完整版（中文群可以用「150 字以内」代替，这是我们的换算建议，不是原文）：

```
在群聊里回复时：
- 单次回复不超过【100 词 / 150 字】。
- 只在需要对方决策或验收时才发消息；进度更新不发。
- 只问直接的问题，只给简短结论，不贴推理过程、不贴工具调用。
- 完整说明写到【PR 描述 / 文档 / 工单】里，群里只发一句结论 + 链接。
- PR 描述按三段写：问题背景、改动说明、验证结果。
```

## 四、委派提示词两段（原文）

原文实验里拿来对比的两段，用在「只有一个主会话 + 子代理工具」的情况（比如 Claude Code 主会话）。原文本身就以省略号截断，下面照原样给出，后面附中文意思。

中性版（原文实验里，5 次运行模型一次都没委派）：

```
Use a subagent for a piece of work when appropriate...
```

中文意思：合适的时候，把一块工作交给子代理去做。

优先委派版（原文实验里，5 次有 4 次委派、1 次自己干了）：

```
Every message of the chat reaches you, so work you run yourself keeps stopping for new messages. Prefer handing each piece of work to a subagent of its own, and do only small things yourself...
```

中文意思：聊天里每条消息都会到你这里，你自己干的活会被新消息不停打断。优先把每件活交给一个单独的子代理，你自己只做小事。

注意：作者的结论是，单会话里分不分工要看提示词和模型临场判断，不稳定；想要稳定，就在系统层面把「前台不干活」定死（比如不给前台执行命令的工具）。

## 五、巡查清单（给长时间跑的任务）

原文 Watchdog 看两类问题：基础设施是不是活着，任务本身有没有进展。下面是按这个思路整理的检查项，阈值是我们给的示例值：

基础设施（用脚本查，不用模型）：
- [ ] 进程 / 定时任务还活着吗
- [ ] 最近【30】分钟有没有接口报错、限流、额度用尽
- [ ] 上次中断后状态有没有恢复成功（进度文件、数据库记录能读到）
- [ ] 等某台电脑上线才能跑的活，那台电脑现在在线吗

任务进展（可以让模型判断）：
- [ ] 每个在跑的任务，最近【30】分钟有没有产出新东西（文件、提交、结论）
- [ ] 有没有原地打转：同一个报错连续出现【3】次以上，或同一条命令反复重跑
- [ ] 方向有没有偏：现在做的事还对得上最初的任务描述吗
- [ ] 有没有两个任务在改同一个文件 / 同一个 PR

发现问题怎么办：
- 原地打转、跑偏：停掉，写一句原因交回分派员重新派
- 外部偶发故障：记下来，下一轮再查，恢复了就关掉
- 需要人拍板：按「三、群聊回复规范」发一条

巡查提示词（贴给定时触发的那个检查会话）：

```
你是巡查员，每【30】分钟被叫醒一次。读取【进度文件 / 任务列表 / 日志路径】，按下面清单逐项检查，
只汇报有问题的项，每项一行：任务编号 | 问题 | 建议动作（停掉重派 / 继续观察 / 需要人拍板）。
全部正常就只回复「正常」。不要自己修改任何任务的代码。
```

## 注意

- 接进群聊等于让 AI 读到不可信的输入。别把密钥、账号密码放进它能读到的地方；能执行命令的那一层，权限越小越好（原文也把这列为没解决的问题）。
- 先上第一道规则筛，再上第二道模型筛。只上第二道，每条消息都调一次模型，又慢又贵。
- 原文提到部分设计在 dsh-superagent-prototype 插件里实现，是验证路线的原型；我们没装、没测，这份模板不依赖它。
- 原文实验数字（P95 15.7 分钟 vs 29.5 分钟、每决定 1.6 秒）是作者在合成负载下的初步结果，别拿去当承诺。
